和 fff 的差距（也是轻量化优化空间）：

最便宜的修复：refresh 在白扔缓存。worker.rs:57-58 里 Command::Catalog 分支开头无条件 cached_roots = None——也就是说每次手动“刷新应用与文件列表”或重载配置，都会把热文件索引作废、下次搜索全量重建 10 万条。应用目录（开始菜单）和搜索目录其实是两份数据，解耦开、catalog 重扫时保留 FileIndex，一行级别的改动就能省掉最大的浪费。
增量更新缺失。文件系统一变（装了新应用、新下载了文件），唯一手段是全量重扫。轻量做法是加 notify crate 的 watcher，只 watch application_roots() 和 search_roots，事件防抖后增量增删 FileIndex.candidates——watcher 的内存开销是 KB 级，比任何缓存都轻，还能顺手干掉“刷新”按钮的存在必要。
索引不落盘。进程重启后第一条文件搜索要冷重建。轻量做法：索引用 serde 序列化到缓存目录（10 万条也就几 MB），启动时加载 + 后台校验。注意它其实已经为这个铺了路——Candidate 全是普通 String/PathBuf，直接可序列化。
内存占用可以再压（但优先级最低）。Candidate 里同一路径存了三份字符串（id、detail、path，search.rs:318-329），10 万条约几十 MB。fff 的 arena/String-pool 思路可以学：路径字符串只存一份、条目里用偏移引用。只在实际测到内存成为问题时再做。
明确不建议学的：内容缓存。search.rs:359 的注释 never build a content index 是有意的设计——内容搜索走流式扫描、每批上限、单文件大小上限（search.rs:399-406）。对启动器来说这是正确的轻量化选择，fff 的内容索引（每文件 360 字节、大仓库几百 MB 常驻）是给“高频反复 grep 同一代码库”的 agent 场景用的，不适合这里。
